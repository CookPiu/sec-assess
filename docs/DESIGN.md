# 自动化安全评估系统 实现方案

需求原文见 [需求说明.md](需求说明.md)（项目实战 2.5），规格、决策记录与假设见 [SPEC.md](SPEC.md)，文中 D-0xx、FR-0xx、SC-0xx 均指 SPEC.md 中的编号。

## 1. 范围与边界

- 评估对象是用户上传或指定 Git 地址的源码工程。动态验证只在本系统创建的隔离容器内、针对该容器里启动的工程副本进行，容器不接外网，系统不提供对任意外部地址发起探测的功能。
- 首版完整支持 Python Web 工程（Flask）；侦察阶段能识别 Java、Node.js 等技术栈并给出依赖清单，但静态污点分析和动态验证只覆盖 Python。
- 靶场是两个自写的教学用 Flask 工程（电商后台、用户中心服务），内置两个示例场景所需的漏洞类型，只在沙箱里运行（D-013）。

## 2. 技术栈

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 后端 | Python 3.12 + FastAPI + SQLAlchemy + uv | 与现有项目一致 |

## 4. 沙箱设计

每个评估任务一个容器，配置固定为：

- 源码以只读方式挂载到 `/src`；需要运行工程时复制到任务专属 Docker 卷 `/work`（工程副本与虚拟环境），写操作只发生在副本里，卷随容器一起删除（D-016）。`/tmp` 为 64 MB tmpfs。
- 根文件系统只读，`--network none`，丢弃全部 capabilities，`no-new-privileges`，非 root 用户运行。
- CPU、内存、进程数上限和任务总超时从配置页读取。
- 依赖准备（D-012）：宿主机用后端虚拟环境里的 pip，按 `requirements.txt` / `pyproject.toml` 执行 `pip download --only-binary=:all: --python-version 3.12`，`--platform` 取沙箱镜像 glibc 对应的 manylinux 标签（在任务容器内读取 glibc 版本得到），只取预编译 wheel，不执行任何构建脚本。整批下载失败时逐个重试以找出拿不到 wheel 的包，连不上索引时不再重试。wheel 缓存在 `data/wheelhouse/`，以只读方式挂到容器的 `/wheels`，由容器内 `pip install --no-index --find-links /wheels` 装进 `/work/venv`。某个包只有源码包或下载失败时改用镜像预装的版本；仍有缺失则跳过动态验证，相关漏洞保持“疑似”。PyPI 地址可在配置页改为镜像源。
- 停止任务时后端直接 `docker kill` 并删除容器和任务卷，已写入数据库的阶段结果保留，任务状态置为 `stopped`；流水线中后续的容器调用失败后按已停止收尾。
- 资源指标通过 Docker stats 接口每 2 秒采样一次，经 SSE 推到前端。
- 隔离自检（SC-007）：集成测试在容器内尝试访问外部地址、写 `/src`、以 root 身份执行，三者都必须失败。网络隔离策略固定为 `none`，配置页只展示；并发任务数默认 1，超出的任务保持 `created` 排队（D-019）。
- 后端启动时清理带本系统标签的遗留容器和卷，并把遗留的 `running` 任务置为 `failed`。

## 5. 流水线

```
recon → code_audit → poc_verify → exploit_chain → report_gen
```

任务状态：`created` → `running` → `completed` / `failed` / `stopped`。每个阶段开始和结束都落库并推送事件，停止信号在阶段之间和每个验证用例之间检查。

### 5.1 环境侦察（recon）

Git 项目首次评估时在本阶段浅克隆仓库（失败则任务置为 `failed`），zip 项目在上传时已同步校验并解压；源码就绪后创建任务容器并开始资源采样。

确定性解析 `requirements.txt`、`pyproject.toml`、`package.json`、`pom.xml` 等，统计代码行数，用 AST 提取 Flask 路由表（URL、方法、处理函数、装饰器）。测试代码（`tests/`、`test/`、`testing/` 目录与 `test_*.py`、`*_test.py`、`conftest.py`）不参与路由提取和后续审计（D-020）。大模型只负责把结果整理成侦察摘要。

同时记录后续阶段要用的事实，存为任务的侦察结果：

- 启动方式：`app.run` 所在模块或 `create_app` 工厂，以及监听端口。
- 各路由的访问前提：无装饰器为匿名，登录装饰器为普通用户，管理员装饰器或角色判断为管理员。
- 注册与登录接口及其读取的字段名，供越权验证自动注册测试账号。
- 用户表是否含密码字段，密码以明文、无盐哈希还是加盐哈希存储；会话是否用 Flask 签名 Cookie。

Python 工程在本阶段末尾完成依赖准备（第 4 节），准备结果写入日志。

### 5.2 源码审计（code_audit）

1. 污点引擎按文件并行解析全部 Python 文件，建立函数级调用图，从 Source（请求参数、表单、JSON、文件、Header、Cookie）沿赋值、拼接、函数参数和返回值传播，到达 Sink（SQL 执行、命令执行、反序列化、文件路径操作、模板渲染等）且途中没有经过已登记的净化函数时，生成一条候选漏洞，并记录每一步的文件、行号和变量名。拼接包括 `+`、f-string、`%` 和 `str.format`；跨文件调用最多追 3 层，类属性、容器元素和动态调用不追踪（D-018）。带 `int`、`float`、`uuid` 转换器的 URL 参数只能取对应类型的值，不作为污点。
2. 鉴权类问题单独规则：需要登录的普通用户路由带资源 ID 参数，处理函数用它查询数据，而处理函数及其直接调用的工程内函数里都没有按当前用户过滤或比对，记为越权候选；匿名可访问、不是注册登录类接口的路由查询用户数据，记为缺失鉴权候选。
3. 敏感信息规则：硬编码密钥、调试开关、对外暴露的配置文件，以及侦察得到的明文或无盐哈希密码存储。
4. 审计 Agent 拿到每条候选及其上下文代码，由大模型判断是否误报、归类并给出 CVSS 3.1 向量；分数由程序按 3.1 基础分公式从向量计算（D-015）。结论附理由，状态统一为 `Unverified`；模型判为误报的放入“模型判定误报”分组，不计入评分。研判默认 4 路并发。
5. 发给模型的只有候选所在函数和污点轨迹涉及的代码片段。模型不可用或在配置页被关闭时，按漏洞类别的默认向量计分，理由标注“未经模型研判”。

### 5.3 动态验证（poc_verify）

- 验证 Agent 按侦察得到的启动方式在沙箱内启动工程副本，从路由表和污点轨迹中确定入口和参数。用例以两个靶场为可靠性基准，对其他 Flask 工程尽力而为，验证不了的保持“疑似”（D-018）。
- 容器没有网络，宿主机无法直连容器端口。探针由挂进容器的执行脚本发往容器内 `127.0.0.1`，宿主机通过 `docker exec` 下发用例 JSON、取回请求与响应原文（D-014）。
- 每类漏洞对应一个验证用例模板，只做“能否触发”的判定。探针里只放算式或随机名，响应中出现计算结果才算命中，以排除输入被原样回显造成的误判：

| 类别 | 无害探针 | 命中特征 |
| --- | --- | --- |
| SQL 注入 | UNION 注入数据库版本函数（SQLite 为 `sqlite_version()`），拼接随机标记 | 响应出现版本字符串与标记 |
| 命令注入 | 注入 `echo $((a+b))`，a、b 为随机数；接口不回显时改为在 `/tmp` 创建随机名空文件 | 响应出现 a+b 的结果，或容器内该文件存在 |
| 模板注入 | 注入 `{{a*b}}` | 响应出现 a*b 的结果 |
| 反序列化 | pickle 载荷通过 `__reduce__` 调用内置 `open`，在 `/tmp` 创建随机名空文件 | 容器内该文件存在 |
| 文件上传 / 路径穿越 | 上传随机名的文本文件，文件名带 `../` | 文件出现在上传目录之外（仍在 `/work` 内） |
| 越权（IDOR） | 用自动注册的测试账号 A 请求账号 B 的资源 | 响应含 B 注册时写入的随机标记 |
| 缺失鉴权 | 匿名请求 | 响应含测试账号的随机标记 |
| 调试模式 | 请求会触发异常的参数 | 响应含 Werkzeug 调试页特征 |
| 配置暴露 | 匿名请求配置接口或文件 | 响应含源码中出现的密钥值 |

- 越权与缺失鉴权需要测试账号：验证 Agent 用侦察得到的注册与登录接口，在工程副本里注册两个随机账号；工程没有注册接口时这类候选保持“疑似”。
- 管理接口无法匿名触发：验证 Agent 从源码的种子账号列表里提取用户名和密码，用工程自身的登录接口取得管理员会话，再执行管理类用例；识别不到账号时这些候选保持“疑似”（D-022）。
- 用例只读写 `/work` 中的工程副本和 `/tmp`，不建立持久化访问。某个用例导致工程进程退出时记为未命中，重启副本后继续。
- 请求原文、响应原文、命中特征和重放用的用例 JSON 作为证据保存。命中特征的改为 `Verified`；未命中但模式存在的保持 `Unverified`，严重与高危降为中危，中危及以下保持原等级。硬编码密钥这类只能静态发现的问题保持 `Unverified`。

### 5.4 攻击路径推演（exploit_chain）

每类漏洞登记前置条件（匿名 / 普通用户 / 管理员）和获得的能力（读数据、拿到管理员身份、写文件、执行代码）。只用已验证漏洞，按“获得能力满足下一步前置条件”连边，生成 DAG；大模型为每条路径写阶段说明和业务危害。路径组装是规则驱动的，模型不参与连边（D-002、D-008）。

漏洞的前置条件取自所在路由的访问前提（5.1），获得的能力按类别登记：

| 类别 | 获得的能力 |
| --- | --- |
| SQL 注入 | 读数据库 |
| 配置暴露 | 读应用密钥 |
| 越权、缺失鉴权 | 读他人数据 |
| 文件上传 / 路径穿越 | 写任意文件 |
| 命令注入、模板注入、反序列化 | 执行代码 |

能力之间的推导规则依据侦察事实：

- 读数据库，且用户表密码为明文或无盐哈希 → 管理员身份。
- 读应用密钥，且会话使用 Flask 签名 Cookie → 管理员身份（伪造会话）。
- 写任意文件，且验证证据显示文件写到了上传目录之外的工程目录 → 执行代码（覆盖源码或模板，进程重载后执行，D-024）。
- 存在开放注册接口 → 匿名者可得普通用户身份。

图的起点是“匿名攻击者”，节点为已验证漏洞和推导出的身份能力，终点为“执行代码”或“读他人数据”。弱密码存储等只能静态发现的问题不作为节点，只写进推导边的说明（D-023）。连边细则：

- 匿名可访问的漏洞从起点进入；需要登录的漏洞优先从“普通用户身份”进入，没有该身份时从“管理员身份”进入；管理类漏洞从“管理员身份”进入。
- 漏洞推导出的身份必须高于进入该漏洞时已有的身份（例如管理员才能触发的 SQL 注入不再推出管理员身份），身份只升不降，图中不会出现环。
- 只保留既能从起点到达、又能到达终点的节点；调试模式这类没有登记能力的漏洞，以及前置条件无法满足或能力衔接不到终点的漏洞，不进图，原因写入阶段日志。
- 从起点到终点经过至少两个漏洞节点的路径作为多步攻击路径输出，最多 30 条，执行代码类排在前面。路径步数计入身份节点。

大模型只拿到路径步骤（节点名、漏洞标题与位置、进入每一步所依据的能力），为每条路径写阶段说明和业务危害；模型不可用、被关闭或输出不合法时，按步骤生成模板文字，并在路径上标明文字来源。

### 5.5 修复补丁与报告（report_gen）

- 大模型针对漏洞所在函数输出修复后的完整函数，由程序用 `difflib` 生成 unified diff，保证格式规范、行号可对。模型不可用时跳过补丁生成。
- 补丁状态只有未采纳和已采纳，研发人员标记采纳时写审计日志；不做补丁回归和审核流（D-017）。
- 安全评分为 100 减去扣分，最低 0 分。每条 Verified 漏洞按严重等级扣分：严重 25、高危 15、中危 8、低危 3；Unverified 隐患按一半扣分；“模型判定误报”不扣分。综合等级按 SPEC.md“假设”中的规则判定。
- 报告按需求 2.5.8 的章节用 Jinja2 模板渲染，导出 Markdown、HTML、PDF。

## 6. 数据模型

| 表 | 关键字段 |
| --- | --- |
| `project` | 名称、来源（git / zip）、技术栈、代码行数、最新评估时间 |
| `task` | 项目、状态、当前阶段、起止时间、容器 ID、资源配额快照、侦察结果（JSON）、依赖准备结果、失败原因 |
| `stage_log` | 任务、阶段、日志行、时间 |
| `finding` | 编号、类型、严重等级、CVSS 向量与分数、文件、行号、验证状态、是否模型判定误报、研判来源（模型 / 默认向量）、研判理由 |
| `taint_step` | 漏洞、序号、文件、行号、代码片段、说明 |
| `evidence` | 漏洞、用例 JSON、请求原文、响应原文、命中特征 |
| `chain_node` / `chain_edge` | 攻击路径图的节点（起点、漏洞、身份能力、终点）与有向边，边上记录所用的能力或推导规则 |
| `attack_path` | 从起点到终点的多步路径：节点序列、攻陷目标、阶段说明、业务危害 |
| `patch` | 漏洞、diff 文本、采纳状态、采纳人、采纳时间 |
| `user`、`audit_log`、`setting` | 三类角色、操作审计、沙箱与模型参数 |

## 7. 前端

- 项目概览：工程卡片、高中低危统计、新建评估弹窗（Git 地址或压缩包上传）。
- 评估工作台三块：阶段步进器 + 日志滚动窗 + 资源曲线；漏洞列表 + 攻击路径图（点节点打开漏洞详情侧栏）；漏洞详情（Monaco 定位到行、污点步骤逐步高亮、请求响应证据、补丁 Diff 与复制 / 采纳按钮）。
- 报告中心：在线预览与三种格式导出。
- 沙箱配置页：镜像列表、网络隔离策略（只展示）、超时、资源配额、并发数、PyPI 地址、大模型参数与开关，仅管理员可见；审计日志查询页同样仅管理员可见。
- 登录后按角色显示菜单和操作按钮，后端接口再校验一次角色。SSE 用 fetch 读取流，以便携带 Authorization 头，令牌不出现在 URL 中。
- 后端与前端开发服务器只监听 `127.0.0.1`。

## 8. 演示场景

预期攻击路径：匿名 → S1 读数据库 → 管理员身份（S5 的无盐哈希）→ S6 / S7 / S8 执行代码，或 → S9 写入工程目录后执行代码；另一组为匿名 → S2 读应用密钥 → 伪造会话得到管理员身份 → 同样四个后台漏洞，共 8 条。用户中心靶场的越权与缺失鉴权各自一步到达“读他人数据”，不构成多步路径。
