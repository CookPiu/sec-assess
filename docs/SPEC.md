# 自动化安全评估系统 规范

状态：已确认 ｜ 规模：完整 ｜ 创建：2026-11-12 ｜ 更新：2026-11-12

关联：[需求说明.md](需求说明.md)（原始需求，项目实战 2.5）、[DESIGN.md](DESIGN.md)（技术方案）、[TASKS.md](TASKS.md)（任务清单）

## 目标

面向 Python（Flask）源码工程的自动化安全评估系统。用户提交 Git 地址或源码压缩包后，系统在隔离容器里依次完成环境侦察、污点分析、无害 PoC 验证和攻击路径推演，输出带文件行号、污点轨迹和验证报文的漏洞证据，以及 Diff 格式修复补丁和可导出的评估报告。使用者是安全工程师、研发人员和系统管理员。验收以需求说明 2.5.10 为准。

## 范围

- 做：
  - 两种接入方式：公开 HTTPS Git 仓库克隆、zip 源码包上传。
  - 技术栈识别覆盖 Python、Java、Node.js 的依赖清单；静态污点分析、动态验证和补丁生成只覆盖 Python Flask 工程。
  - Python 工程的运行依赖由系统自动准备，沙箱容器在整个过程中不联网。
  - 静态分析与动态验证保证在两个靶场上可靠；对其他 Flask 工程尽力而为，验证不了的保持 Unverified。
  - 漏洞类型：SQL 注入、命令注入、服务端模板注入、不安全反序列化、任意文件上传与路径穿越、越权（IDOR 与缺失鉴权）、敏感信息泄露（硬编码密钥、调试模式、配置文件暴露）。
  - 五阶段流水线、实时日志与资源指标、中途停止。
  - 多步攻击路径推演与拓扑图。
  - 修复补丁生成与采纳。
  - 报告预览与 Markdown、HTML、PDF 导出。
  - 三类角色登录与权限、沙箱与模型配置、操作审计日志。
  - 两个教学靶场工程（电商后台、用户中心服务），以电商后台完成端到端演示。
- 不做：
  - 对容器外的任何地址发起探测，包括用户填写的线上环境 URL；系统不提供“输入目标地址扫描”的功能。
  - 在沙箱中实际重放整条攻击链；攻击路径由已验证的单点漏洞按规则推演得出。
  - 获取交互式 shell、植入持久化后门、横向移动等超出“能否触发”判定的利用。
  - 把补丁写回原仓库或提交 PR；“采纳”只记录状态并导出 .patch 文件。
  - Java、Node.js 等技术栈的污点分析与动态验证。
  - 污点分析追踪类属性、容器元素和动态调用。
  - 补丁回归验证与补丁审核流程。
  - 第三方依赖组件的已知 CVE 扫描（SCA）。
  - 私有仓库凭据（SSH key、访问令牌）管理。
  - 多机部署与多租户；系统只在本机运行。

## 使用场景

### US1 新建评估并自动跑完流水线（P1）

安全工程师在概览大盘新建评估，填写 Git 地址或上传 zip。系统建档后自动推进五个阶段，工作台实时显示当前阶段、终端日志和资源曲线，全部阶段结束后任务状态变为 completed，大盘更新该项目的技术栈、最新评估时间和高中低危数量。

单独验证：对电商靶场新建评估，中途不做任何人工操作，任务跑到 completed，过程在工作台可见。

验收：

1. 假如 Docker 已启动且电商靶场以 zip 上传，当工程师点击开始评估，那么任务依次经过 recon、code_audit、poc_verify、exploit_chain、report_gen，最终状态为 completed。
2. 假如任务正处于 poc_verify 阶段，当工程师点击停止，那么沙箱容器被销毁，任务状态变为 stopped，此前已产出的疑似和已验证漏洞仍可查看。
3. 假如任务运行中，那么工作台的日志窗持续追加新日志行，资源曲线持续显示 CPU 与内存占用。
4. 假如用户中心靶场依赖一个预装镜像里没有的包，当评估运行，那么侦察阶段日志列出依赖准备结果，工程在沙箱内正常启动并进入动态验证。

### US2 复核漏洞证据（P1）

审计人员在工作台的漏洞列表查看每条漏洞的 CVSS 评分、分类和验证状态，打开详情后代码视图定位到触发行，可以逐步查看从外部输入到敏感函数的传播轨迹，以及 PoC 请求和响应报文。

单独验证：打开一条已验证的 SQL 注入，能看到触发行、完整轨迹和命中特征的响应报文。

验收：

1. 假如评估已完成，当打开一条 Verified 的 SQL 注入，那么代码视图高亮触发行，轨迹每一步显示文件相对路径、行号和代码片段，证据区显示请求原文、响应原文和命中的特征（例如数据库版本字符串）。
2. 假如某条候选漏洞的 PoC 未命中特征，那么它显示为 Unverified，严重等级不高于中危，并与已验证漏洞分组显示。

### US3 查看多步攻击路径（P1）

审计人员在拓扑图上查看由已验证漏洞串成的攻击路径，点击节点打开该漏洞的详情侧栏。

单独验证：电商靶场评估完成后，拓扑图上至少出现一条三步及以上的路径。

验收：

1. 假如电商靶场评估已完成，那么拓扑图包含“匿名 SQL 注入 → 取得管理员身份 → 后台功能执行代码”这一多步路径，每条边注明前一步获得的能力满足了后一步的前置条件。
2. 假如点击路径上的任一漏洞节点，那么侧栏打开对应漏洞详情。

### US4 导出评估报告（P1）

评估完成后，用户在报告中心预览整篇报告，核对总体等级、已验证漏洞清单和整改优先级，一键导出。

单独验证：对已完成的靶场评估导出三种格式，打开后章节齐全。

验收：

1. 假如评估已完成，当打开报告中心，那么报告包含需求说明 2.5.8 列出的全部章节。
2. 当分别导出 Markdown、HTML、PDF，那么三个文件内容一致，PDF 中的图表和代码块可读。

### US5 查看与采纳修复补丁（P2）

研发人员在漏洞详情里对照 AI 修复补丁的 Diff，确认符合业务逻辑后复制 diff 或下载 .patch 文件，并标记为已采纳。

单独验证：对一条已验证漏洞下载 .patch 并标记采纳，补丁能应用到原工程。

验收：

1. 假如漏洞已验证，那么详情区显示 unified diff 格式的补丁，并左右对比修复前后的代码。
2. 当研发人员点击采纳，那么补丁状态变为已采纳并记入审计日志；下载的 .patch 文件在原工程目录执行 `git apply --check` 无报错。

### US6 系统管理（P3）

系统管理员维护沙箱镜像、网络隔离策略、超时、资源配额、并发任务数和大模型参数，查看操作审计日志。

单独验证：管理员修改单任务超时后，新任务按新值执行。

验收：

1. 假如管理员把单任务超时改小，当新任务运行超过该时长，那么容器被销毁，任务状态为 failed，失败原因为超时。
2. 假如运行中的任务数已达并发上限，当再新建评估，那么新任务保持 created 并排队，有空位后自动开始。
3. 假如以安全工程师或研发人员登录，那么看不到配置页，直接调用配置接口被拒绝。

## 边界情况

- Docker 未启动：新建评估时预检失败，提示沙箱服务不可用，不创建任务。
- Git 克隆失败（地址无效、超时、超出大小上限）：任务状态 failed，日志写明原因。
- zip 含路径穿越条目、符号链接或超出大小上限：拒绝上传并提示原因。
- 工程不是 Python Flask：完成侦察，代码审计只跑敏感信息规则，跳过动态验证，报告注明未覆盖的范围。
- 依赖无法自动准备（宿主机访问不了 PyPI、某个包只有源码包）：改用预装镜像中的同名包；仍有缺失时按“工程无法启动”处理，日志列出缺失的包。
- 工程无法在沙箱内启动：跳过动态验证，相关漏洞保持 Unverified，日志保留启动失败的输出。
- 工程没有注册接口，无法自动准备两个测试账号：越权候选保持 Unverified。
- 某个 PoC 让目标进程崩溃：该用例记为未命中，重启工程副本后继续下一个用例。
- 大模型接口不可用或超时：候选漏洞照常保留，CVSS 采用规则默认值，研判理由标注“未经模型研判”，跳过补丁生成，任务不因此失败。
- 没有发现漏洞：报告等级为“安全”，拓扑区显示无攻击路径。
- 已验证漏洞之间没有能力衔接：不生成多步路径，报告的攻击路径章节写明原因。
- 任务超时：销毁容器，状态 failed，已产出数据保留。
- 后端进程重启时仍有 running 任务：启动时把这些任务置为 failed，并清理遗留容器。

## 需求

- FR-001 支持两种项目来源：公开 HTTPS Git 地址浅克隆，zip 源码包上传；记录项目名称和来源。
- FR-002 侦察阶段识别语言、框架与版本、依赖清单和代码行数；对 Flask 工程提取路由表（URL、方法、处理函数、装饰器）。
- FR-003 每个评估任务使用一个独立容器：源码只读挂载，运行时只写工程副本，容器无外网，非 root 运行，CPU、内存、进程数和总时长受配置限制。
- FR-004 任务状态为 created、running、completed、failed、stopped；阶段按 recon → code_audit → poc_verify → exploit_chain → report_gen 顺序推进，每个阶段的开始和结束都被记录。
- FR-005 停止任务时立即终止沙箱内进程并销毁容器，已产出的阶段数据保留，状态置为 stopped。
- FR-006 静态污点分析跨文件追踪外部输入（请求参数、表单、JSON、上传文件、Header、Cookie）到敏感函数，途中未经过已登记的净化函数时生成候选漏洞，记录每一步的文件、行号、变量和代码片段。传播覆盖赋值、字符串拼接、函数参数与返回值，跨文件调用最多追 3 层。
- FR-007 越权规则：路由带资源 ID 参数、查询时未按当前用户过滤、且没有登录或权限校验时记为越权候选。敏感信息规则：硬编码密钥、调试模式开启、配置文件可被访问。
- FR-008 每条候选漏洞经大模型研判：给出是否误报、漏洞分类、CVSS 3.1 向量与分数和理由；研判后状态统一为 Unverified。
- FR-009 动态验证在沙箱内启动工程副本，对每条候选发送带随机标记的无害探针，响应中出现预期特征时改为 Verified；保存请求原文、响应原文、命中特征和在沙箱内重放的命令。
- FR-010 未命中特征但存在风险模式的候选保持 Unverified，严重等级降到中危或低危。
- FR-011 攻击路径只使用 Verified 漏洞，按“上一步获得的能力满足下一步的前置条件”连边，生成有向无环图；每条路径附阶段说明、攻陷目标和业务危害。
- FR-012 为每条 Verified 漏洞生成 unified diff 补丁，补丁基于原工程文件生成，可直接应用。
- FR-013 补丁状态为未采纳、已采纳，研发人员可以标记采纳；支持复制 diff 和下载 .patch。
- FR-014 工作台实时接收三类更新：阶段变化、日志行、资源指标（CPU、内存、进程数）。
- FR-015 报告包含需求说明 2.5.8 的全部章节，含综合安全等级（极高危、高危、中危、安全）、安全评分、CVSS 分布、漏洞类型占比、已验证漏洞清单、攻击路径和按优先级排序的整改建议；可导出 Markdown、HTML、PDF。
- FR-016 概览大盘列出全部项目（名称、技术栈、最新评估时间、最近一次评估的高中低危数量、评估状态），提供全局统计图和新建评估弹窗。
- FR-017 评估工作台包含流水线与执行监控区、漏洞与攻击链路区、漏洞详情与修复区，内容按需求说明 2.5.3。
- FR-018 沙箱与环境配置页维护镜像、单任务超时、单探针超时、资源配额、并发任务数和大模型参数，并展示网络隔离策略（固定为无网络），仅系统管理员可访问。
- FR-019 用户登录后按角色授权（见“假设”中的权限划分），未登录不能访问任何业务接口。
- FR-020 审计日志记录登录、新建与停止评估、补丁采纳、报告导出和配置修改，含操作人、时间和对象，系统管理员可查询。
- FR-021 提供两个教学靶场工程：电商后台覆盖场景一（注入、命令执行、反序列化、上传、敏感信息），用户中心服务覆盖场景二（越权、缺失鉴权、未授权数据泄露）；两者合计包含范围中列出的全部漏洞类型，并各自带有外观相似但已正确防护的写法，用于演示误报剔除。
- FR-022 侦察阶段按依赖清单自动准备 Python 运行依赖：只获取预编译安装包，在宿主机下载后交给沙箱离线安装，不执行被评估工程或其依赖的构建脚本；准备结果（已装、改用预装、缺失）写入日志和报告。

## 关键实体

- 项目：被评估的一个源码工程，含名称、来源（Git 地址或上传包）、技术栈、代码行数；一个项目可有多次评估任务。
- 评估任务：对项目的一次完整评估，含状态、当前阶段、起止时间、资源配额快照和失败原因。
- 阶段日志：任务在某一阶段产生的一行日志，带时间。
- 漏洞：任务发现的一条问题，含唯一编号、类型、严重等级、CVSS 向量与分数、文件与行号、验证状态（Verified / Unverified）和研判理由。
- 污点步骤：漏洞传播轨迹中的一步，按序号排列，含文件、行号、代码片段和说明。
- 验证证据：一次探针的请求原文、响应原文、命中特征和重放命令，属于一条漏洞。
- 攻击路径：由漏洞节点和带能力说明的有向边组成，属于一次任务。
- 补丁：一条漏洞的 diff 文本和采纳状态。
- 用户、审计日志、系统配置：角色、操作记录、沙箱与模型参数。

## 成功标准

- SC-001 电商靶场从点击开始评估到 completed 全程无人工干预，本机耗时不超过 15 分钟（大模型接口正常时）。
- SC-002 靶场漏洞清单（DESIGN.md 第 8 节）中的每一条漏洞都被检出，预期状态为 Verified 的条目全部达到 Verified；已正确防护的诱饵写法没有一条被标为 Verified。
- SC-003 每条 Verified 漏洞同时具备文件行号、污点轨迹（越权与敏感信息类除外）、请求与响应证据和 diff 补丁；补丁全部通过 `git apply --check`。
- SC-004 电商靶场评估结果中至少有一条三步及以上的攻击路径（步数计入推导出的身份节点，例如“SQL 注入 → 管理员身份 → 后台执行代码”），见 D-023。
- SC-005 日志行从产生到出现在工作台不超过 2 秒，资源指标至少每 2 秒刷新一次。
- SC-006 点击停止后 5 秒内该任务的容器不再存在（`docker ps -a` 查不到），已产出漏洞仍可查看。
- SC-007 自动化测试证明评估容器内访问外部地址失败、写只读挂载目录失败、以 root 身份运行失败。
- SC-008 三种格式的报告都能导出，章节与需求说明 2.5.8 一一对应。
- SC-009 非管理员调用配置与审计日志接口返回 403；研发人员调用新建与停止评估接口返回 403。
- SC-010 两个靶场都能在不手工安装任何依赖的情况下进入动态验证，其中用户中心靶场至少有一个依赖不在预装镜像中。

## 约束

- C-001 动态验证只在本系统创建的隔离容器内、针对容器里的工程副本进行，容器不接外网。（项目 CLAUDE.md）
- C-002 首版只完整支持 Python（Flask）工程。（项目 CLAUDE.md）
- C-003 本机 Windows 11、无 CUDA；Docker Desktop 客户端 29.9.3，使用前需手动启动。
- C-004 本机工具链：uv 0.11.23（已装 CPython 3.12.15）、Node.js 24.19.0、pnpm、Git。
- C-005 真实密钥只放 `.env`，不写入代码、文档、日志或提交。
- C-006 实现范围与取舍以 DESIGN.md 为准，方案变更时同步更新 DESIGN.md 与本文件的决策记录。
- C-007 练手项目，提交时按“组名_姓名_项目_行业”另行复制改名，只放代码（不带依赖）和测试截图。
- C-008 代码、文档、提交中不出现 AI 署名。

## 假设

- 登录用 JWT，预置三类角色各一个账号；所有登录用户都能查看全部项目，操作按角色限制。（已确认）
- 权限划分：安全工程师新建与停止评估、导出报告；研发人员查看结果、采纳补丁、导出报告；系统管理员拥有配置页和审计日志，并可查看全部结果。（已确认）
- Git 只接受公开 HTTPS 地址，在宿主机浅克隆，禁用 hooks、子模块和 LFS；仓库与 zip 解压后都不超过 200 MB，zip 本身不超过 50 MB。（已确认）
- 发给大模型的内容限于候选漏洞所在函数和污点轨迹涉及的代码片段，不发送整个仓库；管理员可关闭大模型，关闭后按规则默认值运行。（已确认）
- 验证证据以 HTTP 报文为准，不另做页面截图。（已确认）
- 默认配额：每容器 1 核 CPU、1 GB 内存、256 个进程，单任务超时 30 分钟，单个探针超时 10 秒。（已确认）
- 综合安全等级：存在 CVSS ≥ 9.0 的 Verified 漏洞或能到达代码执行的攻击路径为极高危；存在 CVSS 7.0–8.9 的 Verified 漏洞为高危；只有中低危或 Unverified 为中危；没有发现为安全。（已确认）
- 大模型研判为误报的候选保留在列表的“模型判定误报”分组，不计入评分和统计。（已确认）
- SC-001 的 15 分钟、SC-005 的 2 秒、SC-006 的 5 秒是按本机演示定的目标值。（已确认）
- 同一项目可多次评估，大盘显示最近一次评估的结果。（已确认）
- 后端和前端只监听 127.0.0.1。（已确认）
- 报告与界面使用中文。（已确认）
- 宿主机能访问 PyPI，或能访问在配置页填写的 PyPI 镜像源。（已确认）
- 越权验证用的两个测试账号由验证阶段通过工程自身的注册接口在副本里注册，不要求用户提供账号。（已确认）
